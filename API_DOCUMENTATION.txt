ATTENDANCE MONITORING API DOCUMENTATION — SECURED MOBILE CONTRACT
===============================================================

Deploy the updated mobile client and backend together. Legacy unauthenticated
mobile requests are no longer accepted. See backend/TRACKING_ROLLOUT.md (or
TRACKING_ROLLOUT.md when reading this file inside backend) for deployment and
physical-device acceptance checks. FastAPI /docs provides the request schemas.

BASE URL AND CONFIGURATION
--------------------------
Use HTTPS in production. Local development may use http://127.0.0.1:8000 or
http://10.0.2.2:8000 for an Android emulator. Do not send credentials over public HTTP.
Run `uvicorn attendance:app` from backend, not the separate face-only server.

Environment:
  SESSION_SECRET=<private random value, at least 32 characters; required>
  SUPERADMIN_EMAIL=<administrator email>
  SUPERADMIN_PASSWORD=<strong private password; no default>
  COOKIE_SECURE=true  (false only for localhost HTTP development)
  MOBILE_TOKEN_TTL_SECONDS=604800
  MONGO_URI=mongodb://localhost:27017/
  DB_NAME=attendance_db
  ONNX_PATH=w600k_r50.onnx
  DEFAULT_TRACKING_TIMEOUT_HOURS=4
  DEFAULT_TRACKING_INTERVAL_MINUTES=30
  AUTO_CHECKOUT_POLL_SECONDS=60

1. HEALTH AND LOGIN
-------------------
GET /health is public.
POST /login accepts JSON {"username":"employee-email-or-id","password":"..."}.
A successful response contains:
  success, access_token, user_type, employee_id, employee_name, org_id,
  is_checked_in, next_attendance_type, active_session_id (when active),
  expected_checkout_at (when active), tracking_settings.

All mobile endpoints below require:
  Authorization: Bearer <access_token>
Use Content-Type: application/json for JSON requests. Let the multipart client
set Content-Type and its boundary for image uploads. Store tokens securely.
Disabled accounts/organizations are rejected even when a token has not expired.

GET /mobile/session returns current identity, attendance state and tracking
settings, without requiring the password again. The client polls this endpoint
and refreshes on resume. A 401/403 stops GPS collection and asks for sign-in.

2. FACE VERIFICATION
--------------------
POST /authenticate (multipart): live_image=file, org_id=organization ID.
A successful match returns authenticated=true, employee_id, employee_name,
org_id, similarity_score, face_token and current attendance state including
active_session_id. The signed face_token expires after two minutes and is bound
to both the matched employee and the authenticated caller. A regular employee
cannot mark attendance for another employee. An organization admin can scan
employees in their own organization, but cannot upload their own phone's GPS
as another employee's periodic tracking.

3. CHECK-IN / CHECKOUT
---------------------
POST /attendance accepts exactly:
  {
    "event_id": "unique-random-id-at-least-16-characters",
    "employee_id": "EMP001",
    "org_id": "org-id",
    "attendance_type": "check_in",
    "latitude": 12.9716,
    "longitude": 77.5946,
    "timestamp": "2026-11-07T04:00:00Z",
    "face_token": "proof-returned-by-authenticate",
    "session_id": null
  }
For check_out, session_id must be the active_session_id from verification/state.
Do not send employee_name; the server obtains it from the authorized profile.
Use a current UTC timestamp (client clock must be within five minutes). Server
receipt time is authoritative for attendance. Required coordinates must be finite
and within latitude [-90,90] and longitude [-180,180].

The response includes success, is_checked_in, attendance_state,
next_attendance_type, active_session_id and expected_checkout_at when active,
and tracking_settings. Apply this state to the UI and persist it before starting
tracking. A tracking startup failure does not undo a successful check-in.

Keep the same event_id when retrying a request after a timeout. Duplicate
requests are idempotent. A new check_in while already active, or checkout for an
inactive/mismatched session, returns 409. Refresh state instead of blindly retrying.

4. LOCATION UPLOAD
------------------
POST /location-track accepts:
  {
    "event_id": "another-unique-random-id-at-least-16-characters",
    "employee_id": "EMP001",
    "org_id": "org-id",
    "session_id": "active-session-id",
    "latitude": 12.9716,
    "longitude": 77.5946,
    "accuracy": 15.0,
    "tracking_status": "ok",
    "timestamp": "2026-11-07T04:30:00Z"
  }
For failed GPS, omit coordinates, set tracking_status="failed", and include a
non-empty remark (maximum 500 characters). Only "ok" and "failed" are accepted.
Only the logged-in employee's own GPS is accepted, including for admin accounts.

The server checks the session and capture timestamp. Offline events may be
uploaded after checkout only when their capture time is within the attendance
session. Unknown sessions or events outside the session return 409. Repeated
uploads with the same event_id do not create duplicate points. The response is
{"success":true,"message":"Location saved"}.

The app sends an immediate point and then samples using tracking_interval_minutes.
Android runs a separate foreground service with a persistent notification. iOS
uses background Core Location updates. Exact execution is controlled by the OS;
force-stop/reboot requires reopening the app. No GPS data is invented for gaps.
GPS errors are stored as failed events. Network outages queue captured events in
secure storage, preserving UTC timestamps and event IDs. On restart, the queue
and schedule are recovered. Pending events retry; invalid events are retained for
diagnosis. Status is visible in the app. Manual and automatic checkout stop capture.

5. AUTOMATIC CHECKOUT
--------------------
When auto_checkout_enabled is true, the backend closes the session at its stored
expected_checkout_at and writes an automatic checkout exactly once. The mobile
app stops capture at that deadline even when offline, and also polls server state.
The timeout setting is snapshotted at check-in; changed intervals are returned
in subsequent session refreshes. With auto checkout disabled, the session remains
active until manual checkout. Session/attendance write reconciliation runs on
backend polling to recover interrupted writes.

6. HISTORY AND ADMIN FACE MANAGEMENT
------------------------------------
GET /attendance-record/{employee_id}?org_id=... returns attendance records.
Regular employees can read only their own records; admins can read their org.
POST /enroll-face (admin only, multipart): employee_id, employee_name, org_id, file.
GET /list?org_id=... (admin only) lists enrolled profiles in the caller's org.
POST /edit/{employee_id} (admin only, form): employee_name and org_id.
DELETE /delete/{employee_id}?org_id=... (admin only).
The server always enforces organization scope; omitted org_id never grants global access.

TIMESTAMPS, MAPS AND FAILURES
----------------------------
New mobile requests require timezone-aware ISO-8601 timestamps. Prefer UTC Z.
Omitted/naive timestamps are rejected. Stored instants are UTC; dashboard dates,
date filtering and display timestamps are IST. Legacy naive timestamps require
an explicit data migration using the original device timezone.

The dashboard refreshes every 30 seconds while visible. Only finite numeric
coordinates in valid ranges are mapped. Failed events are shown as failure
records, never converted to (0,0). Map popup content is rendered as text.
GPS count means successful tracking events; failed GPS count is separate.

WEB DASHBOARD CONTRACT
======================
The following web endpoints use secure session cookies (credentials included),
not mobile bearer tokens. Their JSON request shapes remain compatible.

11. WEB DASHBOARD LOGIN
-----------------------

Endpoint:

  POST /api/auth/login

Headers:

  Content-Type: application/json

Purpose:

  Login for the React web dashboard. This sets a session cookie and is used for
  superadmin, org admin, and user web panels.

Request:

  {
    "username": "admin@example.com",
    "password": "password123"
  }

Optional role request:

  {
    "username": "admin@example.com",
    "password": "password123",
    "role": "auto"
  }

Allowed role values:

  auto
  superadmin
  org_admin
  user

Success response:

  {
    "authenticated": true,
    "role": "org_admin",
    "org_id": "org-id-value",
    "admin_email": "admin@example.com",
    "admin_name": "Org Admin"
  }

Mobile recommendation:

  Use POST /login for normal mobile attendance because it is stateless.
  Use /api/auth/login only if building a mobile version of the admin dashboard
  that supports cookies.

--------------------------------------

Endpoint:

  GET /api/org-admin/attendance

Authentication:

  Requires org admin session cookie from POST /api/auth/login.

Query parameters:

  employee_id  Optional employee filter
  date         Optional exact date in YYYY-MM-DD
  page         Optional, default 1
  page_size    Optional, default 20

  First show the grouped table by employee and date.
  Each row shows check-in count, checkout count, GPS count, failed GPS count,
  first time, and last time.
  When the admin taps a row, open detail/map view for that employee and date.
  Use only date filter for this screen, not from-date/to-date.

14. SUPERADMIN ORGANIZATION SETTINGS
------------------------------------

Endpoint:

  PUT /api/superadmin/orgs/{org_id}

Authentication:

  Requires superadmin session cookie from POST /api/auth/login.

Purpose:

  Edit organization, admin credentials, and tracking configuration.

Request:

  {
    "org_name": "Teal Ops",
    "org_code": "teal-ops",
    "max_users": 50,
    "admin_name": "Org Admin",
    "admin_email": "admin@example.com",
    "admin_password": "",
    "auto_checkout_enabled": true,
    "tracking_timeout_hours": 4,
    "tracking_interval_minutes": 30
  }

Notes:

  Leave admin_password empty to keep the existing password.
  tracking_interval_minutes is controlled here by superadmin.
  Org admin should not edit the interval.

Success response:

  {
    "success": true
  }


15. PAGINATION
--------------

Dashboard list APIs use this format:

  {
    "page": 1,
    "page_size": 20,
    "total": 125,
    "pages": 7,
    "has_next": true,
    "has_prev": false
  }

Mobile/admin UI should request the next page only when has_next is true.


STATUS CODES
------------
200: success
401: missing/expired login or face proof
403: disabled account/organization or wrong employee/organization/role
404: employee not found
409: attendance conflict or GPS outside the specified session
413: image too large
422: invalid coordinates, timestamp, payload, or failed-event remark
500/503: server failure; preserve pending GPS and retry with the original event ID
